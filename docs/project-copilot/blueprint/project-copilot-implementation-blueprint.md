## 1. Objective

### Purpose of this document

This blueprint translates the findings of the Project Copilot integration audit into a phased, executable plan for this repository. It is intended to be used as the primary reference during implementation: for architectural alignment between sessions, for tracking progress, for test planning, and for making scoping decisions under pressure.

This is not a generic AI module guide. Every recommendation in this document is grounded in the actual files, patterns, constraints, and conventions of the ClearQueue codebase.

### What Project Copilot is

Project Copilot is an AI-powered planning assistant that lives inside a project context, accessible as a module tab. Its core purpose is to help a user transform a vague project idea or goal into structured, actionable project data — stages, milestones, tasks, and notes — through a contextual conversation.

It is not a generic chatbot. It understands the current state of the project (existing tasks, notes, resources), asks clarifying questions when scope is vague, proposes structured outputs, and ultimately helps the user create real entries in the system through a controlled approval flow.

The unique product value is: **natural language planning becomes structured project data inside the app.**

### What success looks like for V1

V1 is successful when a user can:

1. Open the Copilot tab inside a project
2. Describe a project idea or goal in plain language
3. Receive a contextually aware response that incorporates the project's existing state
4. See structured planning proposals (tasks, notes) generated by the AI
5. Approve individual proposals and have them created as real entities in the system
6. Return to the board or notes tab and see those entities waiting for them

V1 does not need milestones, session management, plan versioning, or strategic recommendations. It needs the core loop to work reliably: chat → propose → approve → create.

## 2. Scope Definition

### In Scope for V1

- Project Copilot as a toggleable module in the existing module registry (`'copilot'` key)
- One planning session per project (no multi-session management in V1)
- Persistent chat message history (survives tab switches, page reloads)
- AI responses that are contextually aware of the project's existing tasks and notes
- Structured proposal generation for two entity types: **tasks** and **notes**
- Proposal review UI (approve / reject per proposal)
- Server-side validated write path: approved proposals create real `tasks` or `notes` rows
- Rate limiting on AI endpoint (per-user per-day cap)
- Sentry error observability on all AI paths
- i18n for all new UI strings (English and Spanish)
- Shimmer skeleton for loading states
- Basic unit and Playwright happy-path tests

### Out of Scope for V1

- Milestone proposals (no `milestones` table exists; building it is a separate dependency)
- Stage/phase proposals that write to the board structure
- Multi-session management (session list, named sessions, session history browser)
- Plan regeneration / iteration / "revise this plan"
- AI-detected project gaps or health warnings
- External resource / link recommendations
- Bulk approval ("approve all")
- Auto-approval without user confirmation
- Token usage dashboard or cost tracking UI
- Feedback mechanism (thumbs up/down, regenerate)
- AI tool use / function calling (use structured JSON output via prompt instead)

### Future Expansion Opportunities

These are explicitly deferred, not forgotten:

- **Phase 4:** Milestone proposals (requires milestone table to be built first)
- **Phase 4:** Session management UI (multiple sessions per project, named, archived)
- **Phase 4:** Project gap detection ("you have 0 notes — add a scope note")
- **Phase 5:** Plan iteration — AI can reference previous proposals and revise
- **Phase 5:** Cross-project insights ("similar projects took 3 months")
- **Phase 6:** Learning resource recommendations and external link suggestions
- **Phase 6:** AI-assisted project health scoring

## 3. Current Repo Constraints and Reuse Opportunities

### Architecture we can reuse directly

**Module system** (`lib/modules/registry.ts`, `app/actions/modules.ts`, `supabase/migrations/20260302120000_project_modules.sql`):
The registry is built for extension. Adding `'copilot'` as a `ModuleKey` and one entry to `MODULE_REGISTRY` is enough to make the tab bar, settings drawer toggle, and module gating work automatically. No changes to the module infrastructure are needed.

**Context tab pattern** (`app/context/[projectId]/calendar/` is the most recent full example):
`ContextCalendarFromCache.tsx` + `ContextCalendarClient.tsx` is the direct template for `ContextCopilotFromCache.tsx` + `ContextCopilotClient.tsx`. The page structure, cache key registration in `ContextDataCache.tsx`, requireAuth in `page.tsx`, and skeleton usage are all copy-adaptable.

**Project resource aggregation** (`app/actions/projects.ts:515 getProjectResources`):
This function already fetches notes, budgets, boards, and todo lists for a project in a parallel call. It is the natural foundation for the AI context builder. The `buildProjectContext` function in `lib/copilot/context.ts` will call this (or the underlying getters) to assemble the system prompt.

**Write actions** (tasks: `app/actions/tasks.ts`, notes: `app/actions/notes.ts`):
`createTask` delegates to `create_task_atomic` RPC. `createNote` is a clean single insert. Both are the exact write targets for approved proposals. Do not bypass them — route approved proposals through these existing actions.

**Error handling** (`components/board/MutationErrorDialog.tsx`):
The `MutationErrorDialog` pattern (open, title, message, onTryAgain, onCancel) should be used for proposal write failures. Do not use `alert()`.

**Observability** (`lib/sentry.ts` `captureWithContext`):
All AI endpoint error paths must use `captureWithContext` with `module: 'copilot'`, `action`, `userIntent`, `expected`. This is required by AGENTS.md and is already the convention for every server action in the repo.

**i18n** (`lib/i18n.ts`, `locales/en.json`, `locales/es.json`, `components/shared/I18nProvider.tsx`):
All Copilot UI strings must be added under a `copilot.*` key namespace in both locale files. Use `useI18n().t(key)` in all client components.

**Auth** (`lib/auth.ts` `requireAuth`):
Every server action and API route handler must call `requireAuth()` as its first line. This is non-negotiable and already the standard.

### Patterns we must follow

- Every new server action: verb-first name, no `Action` suffix, `requireAuth()` first, explicit `.select()` columns, `revalidatePath` after mutations, return `{ data?, error? }` or `{ ok, data? }`
- Every new context tab: `*FromCache → *Client` with `onRefresh` prop passed down
- Every new migration: timestamp prefix, RLS (all four policies), `updated_at` trigger, compound indexes, FK with CASCADE
- Every new loading state: shimmer skeleton, no spinners, no "Loading..." text
- Every new mutation error: `MutationErrorDialog` pattern, no `alert()`
- Multi-step writes: must be atomic via Postgres RPC with `_atomic` suffix

### Constraints to design around

**Streaming is incompatible with Server Actions in Next.js 14.**
Server Actions cannot stream tokens to the client. The AI chat endpoint must be a Route Handler (`app/api/copilot/[projectId]/chat/route.ts`) that returns a streaming response. This is the only place in the repo that uses SSE or chunked streaming — a new pattern must be established and documented.

**The session cache (`ContextDataCache.tsx`) is in-memory and not appropriate for chat history.**
All other modules use the session cache to avoid refetching data when switching tabs. For Copilot, this is wrong: chat history grows with each turn, and the source of truth is the database. The `ContextCopilotFromCache.tsx` must explicitly NOT use the session cache for message history. It should fetch from DB on every tab visit. This is an intentional exception and must be documented in the component header.

**No milestones table exists anywhere in the repo.**
Confirmed by inspecting `lib/supabase/types.ts` and all migrations. The audit document (`docs/audits/milestone-feasibility-audit.md`) also confirms this. Milestone proposals cannot be built until a separate migration creates the milestones entity. This is a hard V1 blocker for milestone support — which is why milestones are out of scope for V1.

**No rate limiting infrastructure exists.**
The current codebase has zero rate limiting on any endpoint. For the AI API route, rate limiting is a P1 requirement before production launch. It must be implemented as a simple DB-counted check (count rows in `copilot_messages` per `owner_id` in the last 24 hours) until a dedicated rate limiting layer is built.

**`project_modules` uses `(supabase as any)` cast in `app/actions/modules.ts`.**
The `project_modules` table was added after `lib/supabase/types.ts` was last generated. The same pattern (`(supabase as any)`) will likely be needed for the three new Copilot tables until `types.ts` is regenerated. Follow the existing pattern rather than fighting it.

### Prep work needed before starting

1. **Decision:** Install `@anthropic-ai/sdk` — Anthropic's official SDK. This is the only AI package needed. Nothing else can proceed without it.
2. **Decision:** Define the `CopilotProposal` TypeScript type and the JSON schema for `task` and `note` proposals. This drives the parser, validation, and write pipeline.
3. **Decision:** Write and test the system prompt draft manually (raw API call, no code) before implementation begins. The prompt is the highest-leverage variable in the whole system.
4. **Action:** Add `'copilot'` to `ModuleKey` in `lib/modules/registry.ts` as its own standalone PR. This unblocks routing and tab bar work for all other developers immediately.
5. **Awareness:** The milestones table does not exist. If milestones are added to scope during implementation, a separate migration must be created first.

## 4. Target Architecture for Project Copilot

### Frontend surface

A single context tab mounted at `/context/[projectId]/copilot`. The tab appears in the tab bar only when the Copilot module is enabled for the project. The tab renders a full-height chat panel with a fixed input bar at the bottom. Proposal cards are embedded inline in the message thread, directly below the assistant message that generated them.

### Module entry point

```
app/context/[projectId]/copilot/
  page.tsx                      <- requireAuth() + <ContextCopilotFromCache projectId={params.projectId} />
  ContextCopilotFromCache.tsx   <- loads session + messages from DB; no session cache; shows SkeletonCopilot on load; renders ContextCopilotClient
  ContextCopilotClient.tsx      <- owns all UI state; calls streaming API; handles proposals
  actions.ts                    <- all server actions for this tab
```

### Backend / service layer

```
app/api/copilot/[projectId]/chat/route.ts
  <- POST handler
  <- requireAuth() / getUser()
  <- validates projectId ownership
  <- calls buildProjectContext(projectId)
  <- calls AI SDK streamText with context + conversation history
  <- returns SSE stream to client
  <- saves completed assistant message to DB after stream ends (either in route or via a follow-up action call from client)

app/context/[projectId]/copilot/actions.ts
  <- getCopilotSession(projectId)
  <- getCopilotMessages(sessionId)
  <- createCopilotSession(projectId)
  <- saveCopilotMessage(sessionId, role, content, tokenCount?)
  <- saveCopilotProposals(sessionId, messageId, proposals[])
  <- approveProposal(proposalId)
  <- rejectProposal(proposalId)
```

### AI orchestration flow

```
1. User types message in CopilotInputBar
2. ContextCopilotClient optimistically adds user message to UI
3. Client calls saveCopilotMessage (server action) to persist user message
4. Client calls POST /api/copilot/[projectId]/chat with { sessionId, messages: last N turns }
5. Route handler calls buildProjectContext(projectId) -> system prompt string
6. Route handler calls streamText(model, { system, messages })
7. Token stream flows back to client via SSE; CopilotChatWindow renders tokens as they arrive
8. On stream complete: client calls saveCopilotMessage to persist assistant message
9. lib/copilot/parser.ts parses assistant content for JSON proposal blocks
10. If proposals found: client calls saveCopilotProposals to persist them as pending
11. Proposals render as CopilotProposalCard components below the assistant message
```

### Structured output flow

The AI is instructed (via system prompt) to emit structured proposals in a clearly delimited JSON block format:

```
<<PROPOSALS>>
[
  { "type": "task", "title": "...", "status": "next", "priority": 3, "notes": "..." },
  { "type": "note", "title": "...", "content": "..." }
]
<</PROPOSALS>>
```

`lib/copilot/parser.ts` extracts everything between the delimiters, attempts JSON.parse, validates each item against its type schema, and returns a `CopilotProposal[]`. If extraction or parsing fails, an empty array is returned silently — no crash, no user-visible error.

### Validation / write pipeline

```
User clicks "Approve" on a CopilotProposalCard
  -> calls approveProposal(proposalId) server action
  -> action loads proposal row from DB
  -> action validates payload against type-specific schema in lib/validation/copilot.ts
  -> if type === 'task': calls createTask (existing app/actions/tasks.ts)
  -> if type === 'note': calls createNote (existing app/actions/notes.ts)
  -> on success: updates copilot_proposals.status = 'approved', stores created_entity_id
  -> revalidatePath for the affected tab (/context/[projectId] for tasks, /context/[projectId]/notes for notes)
  -> returns { ok: true, createdEntityId, entityType }
  -> client updates proposal card to show "Created" state with link to entity
```

This is a multi-step write. It must be implemented as `approve_copilot_proposal_atomic` Postgres RPC, or the server action must handle the failure of each step with explicit rollback logic. See Section 8 for the recommended approach.

### Persistence model

Three new tables: `copilot_sessions`, `copilot_messages`, `copilot_proposals`. See Section 5 for full definitions.

### Logging / auditability

- Every AI call: `captureWithContext` on any error from the model call or stream failure
- Every `approveProposal`: `captureWithContext` on validation failure or write failure
- `copilot_proposals.reviewed_at` is set when approved or rejected, giving an audit trail of what was generated vs. what was actually created
- `copilot_proposals.created_entity_id` links every created entity back to its AI origin

### Relationship to existing entities

| Copilot entity           | Writes to           | Via                                    |
| ------------------------ | ------------------- | -------------------------------------- |
| Approved `task` proposal | `tasks` table       | `createTask` in `app/actions/tasks.ts` |
| Approved `note` proposal | `notes` table       | `createNote` in `app/actions/notes.ts` |
| Session                  | `copilot_sessions`  | `createCopilotSession` action          |
| Message                  | `copilot_messages`  | `saveCopilotMessage` action            |
| Proposal                 | `copilot_proposals` | `saveCopilotProposals` action          |

Copilot reads from:

- `projects` (name, category, notes field, client info)
- `tasks` (count by status, recent titles — for system prompt context)
- `notes` (recent titles — for system prompt context)

## 5. Proposed Entities / Data Model

### `copilot_sessions`

**Purpose:** One planning conversation per session. A project can accumulate multiple sessions over time (one per planning sprint), but V1 only surfaces the most recent one.

**Key fields:**

| Field        | Type                              | Notes                                                           |
| ------------ | --------------------------------- | --------------------------------------------------------------- |
| `id`         | UUID PK                           |                                                                 |
| `project_id` | UUID FK → `projects.id` CASCADE   | Scopes the session to a project                                 |
| `owner_id`   | UUID FK → `auth.users.id` CASCADE | For RLS and security scoping                                    |
| `title`      | TEXT nullable                     | Auto-generated or user-named in Phase 4                         |
| `status`     | TEXT                              | `'active'` or `'archived'` — only `active` sessions shown in V1 |
| `created_at` | TIMESTAMPTZ                       |                                                                 |
| `updated_at` | TIMESTAMPTZ                       | trigger-managed                                                 |

**Relationships:** One session has many messages. One session has many proposals.

**Why needed:** Without a session entity, messages cannot be grouped or scoped to a planning context. The session is also the boundary for rate limiting decisions and future history browsing.

---

### `copilot_messages`

**Purpose:** Individual turns in the conversation (user messages and AI responses). The source of truth for what was said. Persisted so history survives tab switches and page reloads.

**Key fields:**

| Field         | Type                                    | Notes                                                     |
| ------------- | --------------------------------------- | --------------------------------------------------------- |
| `id`          | UUID PK                                 |                                                           |
| `session_id`  | UUID FK → `copilot_sessions.id` CASCADE |                                                           |
| `project_id`  | UUID NOT NULL                           | Denormalized for RLS scoping efficiency                   |
| `owner_id`    | UUID NOT NULL                           | Denormalized for RLS                                      |
| `role`        | TEXT NOT NULL                           | `'user'` or `'assistant'`                                 |
| `content`     | TEXT NOT NULL                           | Full message content including any `<<PROPOSALS>>` blocks |
| `token_count` | INTEGER nullable                        | Optional; enables cost tracking in Phase 4                |
| `created_at`  | TIMESTAMPTZ                             | Ordered by this for display                               |

**Relationships:** Belongs to one session. One assistant message may generate many proposals.

**Why needed:** Without persisted messages, conversation history is lost on any navigation. The AI also needs the last N messages as context for each new turn.

---

### `copilot_proposals`

**Purpose:** A structured AI-generated action suggestion that the user can approve or reject. The intermediary state between AI output and real system data.

**Key fields:**

| Field               | Type                                     | Notes                                                      |
| ------------------- | ---------------------------------------- | ---------------------------------------------------------- |
| `id`                | UUID PK                                  |                                                            |
| `session_id`        | UUID FK → `copilot_sessions.id` CASCADE  |                                                            |
| `message_id`        | UUID FK → `copilot_messages.id` SET NULL | Links proposal to the assistant message that generated it  |
| `project_id`        | UUID NOT NULL                            | Denormalized for RLS                                       |
| `owner_id`          | UUID NOT NULL                            | Denormalized for RLS                                       |
| `type`              | TEXT NOT NULL                            | `'task'` or `'note'` in V1; `'milestone'` deferred         |
| `payload`           | JSONB NOT NULL                           | Raw proposed data (matches the shape of the target entity) |
| `status`            | TEXT NOT NULL DEFAULT `'pending'`        | `'pending'`, `'approved'`, `'rejected'`                    |
| `created_entity_id` | UUID nullable                            | Set when approved; the ID of the created task or note      |
| `reviewed_at`       | TIMESTAMPTZ nullable                     | Set on approve or reject                                   |
| `created_at`        | TIMESTAMPTZ                              |                                                            |
| `updated_at`        | TIMESTAMPTZ                              | trigger-managed                                            |

**Relationships:** Belongs to one session, optionally linked to one message. When approved, implicitly linked to an entity in `tasks` or `notes` via `created_entity_id`.

**Why needed:** Proposals are the safety layer between AI generation and database writes. Without them, there is no approval flow and no audit trail of what the AI suggested vs. what the user accepted.

**Migration requirements for all three tables:**

- RLS enabled with SELECT/INSERT/UPDATE/DELETE policies scoped via `EXISTS (SELECT 1 FROM projects p WHERE p.id = project_id AND p.owner_id = auth.uid())`
- `updated_at` trigger using `update_updated_at_column()` (sessions and proposals only; messages are immutable)
- Compound index on `(project_id, created_at DESC)` for all three tables
- Index on `(session_id, created_at ASC)` for messages (chronological load)
- Index on `(session_id, status)` for proposals (load pending proposals for a session)

- `components/skeletons/SkeletonCopilot.tsx`
- Rate limiting check in the API route — **built as part of the route, not added later**. DB-counted: daily limit (30 msgs / 24h) + hourly sub-limit (15 msgs / 1h). Returns 429 with `{ error, limitType, resetAt }` before any model call is made.
- i18n keys: `copilot.title`, `copilot.input_placeholder`, `copilot.send`, `copilot.thinking`, `copilot.empty_state`, `copilot.rate_limit_error`, `copilot.error_message`

**Exit criteria:**

- User can open Copilot tab, type a message, and receive a streaming response
- Response references actual project data (proves context injection works)
- Conversation persists across tab switch to another module and back
- Skeleton shows during initial load
- Rate limit returns a clear error message (not a crash) when exceeded
- All strings use i18n keys
- Playwright test: open Copilot, send a message, receive response

### Phase 2 — Structured planning drafts (proposal generation)

**Goal:** AI can generate structured task and note proposals. User sees them as reviewable cards but cannot approve them yet.

**User-visible outcome:**

- After certain AI responses, proposal cards appear inline in the chat thread
- Each card shows the proposed entity type (Task / Note), title, and key fields
- User can reject individual proposals (they disappear or are marked rejected)
- Rejected proposals do not affect the DB entities

**Technical scope:**

- `lib/copilot/parser.ts` (`parseProposals` function — extracts and validates JSON from assistant content)
- `lib/validation/copilot.ts` (client-side proposal shape validators per type)
- Update system prompt to include structured output instructions and JSON block format
- `components/context/copilot/CopilotProposalCard.tsx` (shows proposal; reject button active; approve button visible but disabled or absent in Phase 2)
- `app/context/[projectId]/copilot/actions.ts` additions: `saveCopilotProposals`, `rejectProposal`
- `ContextCopilotClient.tsx` updates: parse proposals from completed stream, call `saveCopilotProposals`, render `CopilotProposalCard` components
- i18n: `copilot.proposal_task`, `copilot.proposal_note`, `copilot.approve`, `copilot.reject`, `copilot.proposal_rejected`

**Dependencies:** Phase 1 complete (message persistence and streaming working)

**Risks:**

- The parser is the most brittle component in the system. The model will sometimes produce malformed JSON, truncated blocks, or proposals inside the narrative text rather than in the delimited block. The parser must be defensive: return empty array on any parse failure, log the failure to Sentry, never throw.
- The proposal card UI is more complex than it looks. A card must handle pending, rejected, and (in Phase 3) approved states. Design all three states up front even if only pending and rejected are active in Phase 2.

**Exit criteria:**

- When the AI includes a `<<PROPOSALS>>` block, proposal cards appear below the message
- Rejecting a proposal calls `rejectProposal`, updates the card state, and does not write to `tasks` or `notes`
- Malformed AI output does not crash the client
- `lib/copilot/parser.ts` has Vitest unit tests covering valid proposals, malformed JSON, empty blocks, and missing delimiters

### Phase 3 — Validated write actions (approve to create)

**Goal:** Approving a proposal creates a real entity in the system through the existing validated write pipeline.

**User-visible outcome:**

- "Approve" button on proposal cards is active
- After approval, card shows "Created — view on board" or "Created — view in notes" with a navigation link
- The board tab reflects the new task; the notes tab reflects the new note (no manual refresh needed)

**Technical scope:**

- `approveProposal(proposalId)` server action implementation
- `approve_copilot_proposal_atomic` Postgres RPC (or careful multi-step server action with explicit rollback)
- `lib/validation/copilot.ts` additions: server-side payload validators per proposal type (separate from client-side validators in Phase 2)
- Proposal card approve handler in `ContextCopilotClient.tsx`
- Proposal card "Created" state in `CopilotProposalCard.tsx`
- `revalidatePath` for board and notes after successful writes
- Integration test: propose task → approve → verify task exists in `tasks` table

**Dependencies:** Phase 2 complete. The write targets (`createTask`, `createNote`) are already stable.

**Risks:**

- `approveProposal` is a multi-step write: validate payload, call write action, update proposal status, store `created_entity_id`. If any step fails mid-way, the system ends up in an inconsistent state. This is the strongest argument for implementing it as an `_atomic` RPC. If implemented as a server action instead, every step must be wrapped in try/catch with explicit compensating logic.
- Payload validation on the server is distinct from the client-side shape validation in Phase 2. Server validation must be stricter: trim all strings, enforce required fields, reject empty titles, enforce valid status enum values. A proposal with `title: ""` must never reach `createTask`.
- After approval, the cache for the board or notes tab must be invalidated. `revalidatePath` handles the server cache. The client-side session cache (`ContextDataCache`) for the affected tab must also be invalidated. The `onRefresh` callback pattern used in all other modules applies here too — call `invalidateProject(projectId)` to flush all project caches after a write.

**Exit criteria:**

- User approves a task proposal → task appears in board tab without manual refresh
- User approves a note proposal → note appears in notes tab without manual refresh
- Approving a proposal with an invalid payload (manually injected) returns a clear error, not a 500
- `copilot_proposals.created_entity_id` is populated correctly after approval
- `copilot_proposals.reviewed_at` is set on both approve and reject

### Phase 4 — Session management and iterative planning

**Goal:** Users can manage multiple planning sessions, start fresh, and the AI can reference previous proposals when revising a plan.

**User-visible outcome:**

- Session list UI (create new, switch to previous)
- Named sessions (auto-generated titles or user-editable)
- "Start fresh" button to archive current session and begin a new one
- AI is aware of previously approved proposals when asked to revise the plan

**Technical scope:**

- Session selector UI in `ContextCopilotClient.tsx`
- `getCopilotSessions`, session archival action
- System prompt update: include list of approved proposal titles as context
- Milestone proposal type (requires separate milestone table migration)
- Stage proposal type (if board column management exists by this phase)

**Dependencies:** Phase 3 complete. Milestone table migration (separate effort).

**Risks:** See Section 12 for general risks. Phase 4 is explicitly deferred — do not creep it into Phase 3.

## 7. Detailed Implementation Workstreams

### Frontend

**What must be built:**

- `ContextCopilotFromCache.tsx` — follows calendar module pattern exactly; exception: no session cache for messages
- `ContextCopilotClient.tsx` — owns streaming state, proposal state, message list
- `CopilotChatWindow.tsx` — scrollable message container with auto-scroll to bottom on new message
- `CopilotMessageBubble.tsx` — renders user or assistant message; handles streaming cursor; embeds proposal cards
- `CopilotInputBar.tsx` — textarea with submit button; disabled during streaming; handles Enter key
- `CopilotProposalCard.tsx` — approve/reject buttons; pending/approved/rejected states; link to created entity
- `SkeletonCopilot.tsx` — shimmer that approximates the chat panel layout

**Existing files involved:**

- `app/context/[projectId]/calendar/ContextCalendarFromCache.tsx` — direct template
- `components/board/MutationErrorDialog.tsx` — error handling pattern for write failures
- `components/shared/I18nProvider.tsx` — `useI18n()` hook
- `components/skeletons/SkeletonNotes.tsx` — shimmer pattern reference

**Decisions that must be made:**

- How many messages to show on initial load (last 20? all? paginated?)
- Scroll behavior: auto-scroll to bottom on new message, but do not steal focus if user is scrolled up reading history
- Should the input be disabled while waiting for a stream, or allow queuing? (Recommendation: disable during stream for V1)

**What can go wrong:**

- Not accounting for the iOS keyboard pushing content up (the `fixed inset-0` layout can break scroll containers on mobile when the keyboard appears)
- Streaming rendering causing layout jank if the message bubble doesn't have a stable height
- Proposal cards mixed into the message thread making the scroll container jumpy

---

### Backend

**What must be built:**

- `app/api/copilot/[projectId]/chat/route.ts` — POST handler, SSE stream, auth check, project ownership validation
- `app/context/[projectId]/copilot/actions.ts` — all server actions for persistence
- `lib/copilot/context.ts` — `buildProjectContext(projectId)` assembles system prompt
- `lib/copilot/parser.ts` — `parseProposals(content)` extracts proposals from assistant messages
- `lib/copilot/schema.ts` — TypeScript types for all Copilot entities

**Existing files involved:**

- `app/api/documents/[fileId]/view/route.ts` — reference for Route Handler structure and auth pattern
- `app/actions/projects.ts:515 getProjectResources` — called by context builder
- `app/actions/tasks.ts createTask` — write target for approved task proposals
- `app/actions/notes.ts createNote` — write target for approved note proposals
- `lib/auth.ts requireAuth` — first call in route handler
- `lib/sentry.ts captureWithContext` — error reporting

**Decisions that must be made:**

- Where does the assistant message get saved to DB? Two options: (a) the route handler saves it after stream completes, (b) the client calls `saveCopilotMessage` as a follow-up action after stream ends. Option (b) is cleaner because Route Handlers should not call server actions. Recommendation: client calls `saveCopilotMessage` after `onFinish` callback from AI SDK.
- How many previous messages to include in the AI context? Recommendation: last 10 turns (20 messages) as a V1 default. Older history is in DB but not sent to the model.
- Should the system prompt include full task notes or just titles? Recommendation: titles only in V1. Full notes would be too expensive.

**What can go wrong:**

- Forgetting `requireAuth()` in the route handler — auth gap
- Passing the entire `copilot_messages` history to the model without truncation — token cost explosion
- Route handler errors not being caught and reported to Sentry
- Stream ending without the client saving the assistant message (network interruption) — orphaned user message with no response

---

### Database

**What must be built:**

- Three migrations: `copilot_sessions`, `copilot_messages`, `copilot_proposals`
- `lib/supabase/types.ts` updates for all three tables
- Postgres RPC: `approve_copilot_proposal_atomic(in_proposal_id uuid, in_user_id uuid)` — atomically validates, creates entity, marks proposal approved (Phase 3)

**Existing files involved:**

- `supabase/migrations/20260302120000_project_modules.sql` — most recent migration; reference for structure and RLS pattern
- `supabase/migrations/20260224100000_document_hub.sql` — reference for complete migration with enums, RLS, storage, triggers
- `supabase/migrations/20260216010000_atomic_todo_and_task_creation.sql` — reference for `_atomic` RPC pattern

**Decisions that must be made:**

- Should `copilot_messages.content` store the raw assistant output (including `<<PROPOSALS>>` blocks) or only the display content? Recommendation: raw content — it is the source of truth and proposals are re-parsed from it when messages are loaded.
- Should `approve_copilot_proposal_atomic` be a DB-level RPC or a carefully written server action? Recommendation: DB RPC for atomicity guarantee, consistent with AGENTS.md policy.
- Is a soft-delete needed for sessions or messages? Recommendation: no for V1. Hard delete on session cascade-deletes all messages and proposals.

**What can go wrong:**

- Missing RLS on any table — security gap
- Missing `updated_at` trigger — stale `updated_at` timestamps
- Missing `project_id` index — slow queries as data grows
- `payload JSONB` column not indexed — acceptable in V1, but add a GIN index in Phase 3 when proposal queries become more complex

---

### AI Orchestration

**What must be built:**

- `lib/copilot/context.ts` — project context assembler (builds the system prompt string)
- System prompt template (hardcoded in `context.ts`, version-controlled as code)
- Conversation history truncation logic (last N turns)
- `lib/copilot/parser.ts` — proposal extractor with defensive failure handling

**Existing files involved:**

- `app/actions/projects.ts getProjectById` — project name, category, notes field
- `app/actions/tasks.ts getTasksByProjectId` — task data for context
- `app/actions/notes.ts getNotes` — note titles for context

**Decisions that must be made:**

- What goes in the system prompt? Mandatory: product role definition, output format instructions (including `<<PROPOSALS>>` block schema), constraint that AI must not claim it can write directly to the DB (it proposes only). Optional: project category context, business/client name if available.
- What is the token budget for project context? Recommendation: aim for under 1,500 tokens for the system prompt in V1. Tasks: most recent 10 (titles + status only). Notes: most recent 5 (titles only).
- Should the AI be told how many tasks currently exist in each status? Yes — this is the most useful contextual signal for planning conversations.

**What can go wrong:**

- System prompt that is too long eats into the context window and raises costs
- Prompt that doesn't constrain output format leads to inconsistent `<<PROPOSALS>>` placement
- Context builder that fails silently and sends an empty system prompt — the AI will behave generically with no project awareness
- Prompt that changes meaning across updates without version tracking — treat the system prompt as code, not config

---

### Validation and Write Safety

**What must be built:**

- `lib/validation/copilot.ts` — client-side proposal shape validators (Phase 2) and server-side strict validators (Phase 3)
- Server-side validation in `approveProposal` before calling any write action
- Schema types that match `tasks.Insert` and `notes.Insert` exactly so proposal payloads can be mapped cleanly

**Existing files involved:**

- `lib/validation/profile.ts`, `lib/validation/project-links.ts` — validation style reference (no Zod; use trim, length, allowlists)
- `app/actions/tasks.ts createTask` — the exact shape needed for a task proposal payload
- `app/actions/notes.ts createNote` — the exact shape needed for a note proposal payload

**Decisions that must be made:**

- Should `approveProposal` call `createTask` directly (reusing the full server action including FormData handling), or call the underlying Supabase insert directly? Recommendation: call the existing server action. Do not duplicate the write logic. The FormData shape is an implementation detail of the existing action — create a typed wrapper function or extract the DB call to be callable directly.
- What happens if validation fails during approval? Return `{ ok: false, error: 'validation_failed' }` and show `MutationErrorDialog`. Do not silently reject.

**What can go wrong:**

- Forgetting server-side validation and trusting client-side only — AI-generated payloads with empty titles or invalid status enums reach the DB
- Calling `createTask` with a null `project_id` in the proposal payload — Supabase will throw, but the error message will be confusing
- `approved_at` not being set when approval succeeds — audit trail gap

---

### UX / Interaction Design

**Decisions that must be made before implementation:**

- Proposal cards inline in the message thread vs. a separate "Proposals" panel to the side. Recommendation: inline in V1. A side panel adds layout complexity that isn't warranted at this scale.
- Should the user be able to edit a proposal before approving it? (e.g., change the task title before it is created). Recommendation: out of scope for V1. Edit-before-approve is Phase 3+ territory. For V1, approve as-is or reject.
- How does the user signal "start planning this project"? Options: always-on chat (user just types), or an onboarding prompt shown on first open ("Describe your project..."). Recommendation: onboarding prompt on first open (empty session), then open chat after first message.

### Testing

See Section 9 for full testing strategy.

### Observability / Logging

**What must be built:**

- `captureWithContext` calls on: API route stream failure, `approveProposal` validation failure, `approveProposal` write failure, `buildProjectContext` error, `parseProposals` unexpected failure
- Use `module: 'copilot'` consistently for all Sentry tags
- `copilot_proposals.reviewed_at` and `created_entity_id` serve as the audit trail for what was generated vs. accepted

**What can go wrong:**

- Streaming errors that fail silently — the client sees an interrupted stream with no error shown
- Parse failures logged to Sentry but also surfaced to user as a confusing empty state

### Access Control / Permissions

**What must be built:**

- RLS on all three tables (owner via project ownership join, not direct `owner_id = auth.uid()` since we're using the project join pattern consistent with `project_modules`)
- Route handler: validate `projectId` belongs to the authenticated user via `getProjectById` (which already enforces `owner_id = user.id`)
- Module gate: the Copilot page must call `requireAuth()` and the tab bar respects `enabledModuleKeys` from the module system

**What can go wrong:**

- Missing project ownership check in the route handler — user A could send messages to user B's project session
- RLS that checks `owner_id = auth.uid()` without the project join — inconsistent with the rest of the codebase

8. **Build `app/api/copilot/[projectId]/chat/route.ts`** — build the complete route in one step in this exact order of operations:
   - `requireAuth()` / `getUser()` — first line, no exceptions
   - Validate `projectId` ownership via `getProjectById`
   - Validate input: `sessionId` is valid UUID, `messages` array max 20 items, user message max 2,000 chars
   - **Rate limit check (DB-counted, daily + hourly) — before any model call.** The route must not call the model without rate limiting in place. Return 429 with `{ error, limitType, resetAt }` if exceeded.
   - Call `buildProjectContext(projectId)` → system prompt
   - Call `streamText` with context + last 20 messages
   - Pipe stream to client via SSE
   - Add `captureWithContext` on all error paths (`module: 'copilot'`)
   - Test with curl/Postman before building any UI. The route is **not considered done** until rate limiting is verified working.

10. **Build UI shell** — `page.tsx`, `ContextCopilotFromCache.tsx` (explicitly does NOT use session cache — fetch from DB on every visit; see ADR-004), `ContextCopilotClient.tsx` (message list + input only, no proposals). `SkeletonCopilot.tsx`.

15. **Update system prompt for structured output** — add `<<PROPOSALS>>` block instructions and JSON schema.

16. **Add `saveCopilotProposals` and `rejectProposal` server actions** to `actions.ts`.

17. **Build `CopilotProposalCard.tsx`** — pending and rejected states only. Approve button visible but disabled.

18. **Wire proposal generation into `ContextCopilotClient.tsx`** — parse on stream complete, call `saveCopilotProposals`, render cards.

19. **Write `approve_copilot_proposal_atomic` Postgres RPC** — validates payload, calls insert into `tasks` or `notes`, marks proposal approved, stores `created_entity_id`.

20. **Build `approveProposal` server action** — calls RPC, revalidates paths, invalidates session cache for affected tabs.

21. **Activate approve button on `CopilotProposalCard.tsx`** — wire to `approveProposal`, show "Created" state with link.

22. **Integration test** — propose task → approve → verify in `tasks` table → verify board tab updates.

23. **Final polish** — error states, empty states, mobile scroll, edge case handling.

## 11. Open Decisions / Unknowns

These must be resolved before or during implementation. They are listed in order of how early they block work.

**Blocking Phase 0:**

- **AI SDK:** `@anthropic-ai/sdk` — Anthropic's official SDK. Confirmed. Confirm the `ANTHROPIC_API_KEY` environment variable is provisioned for both local dev and production before starting.
- **API key management:** Where does the Anthropic API key live? It must be a server-only environment variable (never exposed to the client). Confirm the key provisioning process for local development and production (Vercel environment variable or Supabase secret).

**Blocking Phase 1:**

- **System prompt quality:** The prompt must be written and validated before coding begins. A poor prompt means Phase 1 will feel broken even if all the code is correct. Allocate dedicated time for prompt iteration.
- **Token budget:** How much project context to inject? Recommendation: 1,500 tokens maximum for the system prompt. Confirm this is acceptable.
- **Message history sent to model:** How many past turns to include? Recommendation: last 10 turns (20 messages). Confirm.

**Blocking Phase 3:**

- **`approveProposal` atomicity approach:** DB-level RPC (`approve_copilot_proposal_atomic`) vs. carefully written server action with compensating logic. The RPC is the safer choice per AGENTS.md policy. Confirm which approach to take before writing Phase 3 code.
- **`createTask` API shape:** `createTask` currently expects a `FormData` object. Calling it from `approveProposal` with a JSONB proposal payload requires either converting the payload to `FormData` or extracting the DB insert logic into a shared helper callable by both the form handler and the approval action. Decide which approach is cleaner before Phase 3.

**Blocking Phase 4:**

- **Milestone table:** If milestone proposals are ever added, a `milestones` table must exist first. This is a separate migration with its own RLS, indexes, and UI. Confirm whether milestones belong in Phase 4 or even later.
- **Multi-session UI:** Should users be able to name sessions? Auto-generate names from the first message? Decide before Phase 4 session UI is built.

**Open product questions:**

- Should the user be able to edit a proposal before approving it (e.g., change task title)? If yes, the proposal card needs an edit mode and the write pipeline needs to handle modified payloads. Recommended decision: no for V1, yes for Phase 3+.
- Should approved proposals remain visible in the chat thread or disappear after approval? Recommended decision: remain visible with "Created" state so the user has a record of what was accepted.
- Should the Copilot tab be enabled by default for all new projects or disabled by default? Recommended decision: disabled by default (consistent with `owner`, `media`, `calendar`, etc.) — the user enables it deliberately.

## 12. Risk Controls

### Hallucinated structure

**Risk:** The model generates proposals with plausible but nonsensical content (a task titled "undefined", a note with no content, a milestone with a date in 1970).

**Control:** Server-side payload validation in `lib/validation/copilot.ts` rejects empty strings, null fields, and obviously invalid values before `approveProposal` calls any write action. No proposal with an empty title ever reaches `createTask`. The user also sees the proposal content before approving — the human review step is the primary control.

---

### Invalid task/note generation

**Risk:** AI generates a task proposal with `status: 'invalid_status'` or a note proposal with a 50,000-character content field.

**Control:** Explicit allowlist validation for `status` (must be one of `BOARD_STATUSES`), `priority` (1–5), and character limits on all text fields. These validators live in `lib/validation/copilot.ts` and run server-side in `approveProposal` before any DB write.

---

### Duplicate entity creation

**Risk:** User double-clicks "Approve" and two tasks are created for one proposal.

**Control:** The `approve_copilot_proposal_atomic` RPC checks that `status = 'pending'` before doing any work. If the proposal is already `'approved'`, the RPC returns an error without writing. The approve button in `CopilotProposalCard.tsx` must be disabled immediately on click (optimistic disable) to prevent double submission.

---

### Bad UX from over-chatting

**Risk:** Users get stuck in an open-ended conversation with no structure, treating Copilot as a general assistant rather than a planning tool.

**Control:** System prompt must explicitly define Copilot's role as a structured planning assistant and instruct the model to guide conversations toward concrete proposals. Rate limiting (max messages per day) also naturally discourages aimless chatting.

---

### Unsafe writes

**Risk:** An AI-generated payload bypasses validation and writes corrupt or unexpected data to `tasks` or `notes`.

**Control:** Three-layer defense:

1. Client-side proposal shape validation (Phase 2) catches obviously wrong shapes before they are saved to `copilot_proposals`
2. Server-side payload validation in `approveProposal` (Phase 3) rejects anything that doesn't conform to the entity schema
3. RLS on `tasks` and `notes` ensures the created row is always scoped to the correct owner and project

---

### Schema drift

**Risk:** The `payload` JSONB in `copilot_proposals` drifts from the actual shape expected by `createTask` or `createNote` as those actions evolve.

**Control:** `lib/copilot/schema.ts` defines proposal payload types that are explicitly mapped to `tasks.Insert` and `notes.Insert`. When `createTask`'s input shape changes, the validator for task proposals must be updated in the same PR. The TypeScript type system will catch mismatches if the mapping is typed correctly.

---

### Maintainability issues

**Risk:** The Copilot module becomes a source of unique patterns that future developers don't understand (streaming, no session cache, JSONB proposals).

**Control:** Document the exceptions explicitly:

- In `ContextCopilotFromCache.tsx`: comment explaining why session cache is not used
- In `app/api/copilot/[projectId]/chat/route.ts`: comment explaining the streaming Route Handler pattern and why a Server Action cannot be used here
- In this blueprint document: all reasoning is preserved for future reference

---

### Runaway complexity

**Risk:** Phase 2 or Phase 3 scope expands to include milestone proposals, session management, or plan regeneration, making the implementation unmanageable.

**Control:** This blueprint explicitly marks those features as out of scope for V1. During implementation, any request to add milestone proposals should be treated as a Phase 4 item and logged separately. The milestone table does not exist; this is a hard stop, not a soft preference.

---

### Runaway AI costs

**Risk:** A small number of users generate thousands of messages, driving up API costs beyond the product's budget.

**Control:** Rate limiting (max messages per user per day) is a required V1 feature, not optional. Additionally, `buildProjectContext` must respect a token budget cap. In Phase 4, add per-project session archival so old sessions stop being sent to the model.

---

## 13. Recommended V1 Delivery Strategy

### The leanest valuable V1

The minimum V1 that delivers real product value is:

1. A working chat interface where the AI understands the project context
2. Structured proposal cards for tasks and notes
3. One-click approval that creates real entities in the system

Everything else — session management, milestone proposals, plan revision, strategic recommendations — can wait. Users get immediate value from the core planning loop: **describe → propose → approve → create**.

### What to delay until Phase 2+

- Milestone proposals (no table, hard dependency)
- Multi-session UI
- Edit-before-approve on proposal cards
- AI-detected project gaps
- Token usage visibility
- Feedback/regenerate buttons

### Is the codebase ready now?

Not immediately. Phase 0 must be completed first:

- AI SDK must be installed
- System prompt must be drafted and validated externally
- Three migrations must be written and applied
- TypeScript types must be defined

None of this is blocking in the sense of requiring refactors to existing code. The existing architecture is clean and does not need to be changed to accommodate Copilot. Phase 0 is pure additive work.

### Recommended implementation posture

**Controlled, phase-gated.** Do not attempt to build Phases 1–3 simultaneously. Complete Phase 0 fully (migrations applied, SDK installed, types defined, prompt validated). Then build Phase 1 to a working end-to-end state before touching proposal generation. Then add Phase 2 on top of a stable Phase 1. This posture reduces integration risk and makes it possible to ship Phase 1 independently as an internal preview while Phase 2 is being built.

The biggest single risk in this project is prompt quality. A bad system prompt cannot be fixed by engineering. Allocate a meaningful amount of time — before writing any code — to designing, testing, and iterating on the system prompt using raw API calls. This is the highest-leverage work in the entire module.
